# 과제 4 — 4단계: 최종 모델 선정

## 최종 모델

**Kanana 1.5 8B Instruct** (카카오) — 사내 GPU 서버 설치 + LoRA 미세조정

## 선정 이유

| 기준 | 내용 |
|---|---|
| 보안 (최우선) | 사내 서버에서 실행 → 사내 문서가 회사 밖으로 나가지 않음 |
| 한국어 | 한국어 데이터로 학습한 국내 모델. 한국어 업무 문서 판정에 적합 |
| 라이선스 | Apache 2.0 → 상업 이용·수정 자유 |
| 최적화 | LoRA 미세조정으로 우리 규칙·문체에 맞춤 가능. 원래 모델은 고정하고 작은 보조 행렬만 학습해 적은 GPU로 가능 |
| 운영 규모 | 8B 크기 → GPU 한 장으로 운영 가능 |

## 후보 비교 결과

| 후보 | 결과 | 이유 |
|---|---|---|
| Claude Sonnet 5.5 | 제외 | 문맥 판단·수정안 품질은 가장 좋지만 사내 문서를 외부 API로 전송해야 함 |
| **Kanana 1.5 8B Instruct** | **선정** | 보안·한국어·상업 이용 조건을 모두 충족 |
| KLUE RoBERTa-large | 단독 제외 (보조 선택) | 인코더라 판정만 가능하고 수정안을 생성하지 못함. 빠르고 결과가 일정해 1차 필터로 조합 가능 |
| (참고) EXAONE 4.5 | 후보 제외 | 한국어 성능은 좋으나 비상업 라이선스(NC) |

## 약점과 보완 방안

| 약점 | 보완 방안 |
|---|---|
| 학습용 정답 데이터가 없음 (현재 샘플 4건) | 가상 문서로 규칙별 「문장 → 판정·수정안」 데이터 구축. 실제 사내 문서를 쓰지 않으므로 데이터 생성 단계에서만 상용 LLM의 도움을 받아도 보안 문제 없음 |
| 작은 모델이라 추론이 필요한 판단(C-06 이유 충분성)은 틀릴 수 있음 | AI 판정은 "권고"로만 분류 → 오판해도 검토 요청을 막지 않음 (중간평가 설계 원칙) |
| GPU 서버 구축·운영 부담 | 8B 모델로 GPU 한 장 규모. 필요 시 KLUE RoBERTa 1차 필터로 LLM 호출량 감소 |

## 적용 구조

```
문서 입력
  → 코드 판정 (형식 규칙 4개: C-01, C-02, C-05, P-01) ── 필수
  → Kanana 1.5 8B + LoRA (문맥 규칙 5개: C-03, C-04, C-06, M-01, P-02) ── 권고
       └ 규칙 9개 원문을 프롬프트에 전부 포함 (규칙이 적어 RAG 불필요)
  → 판정 상태: 필수 0건이면 검토 요청 가능
```

- 규칙이 수백 개로 늘거나 회사별 규칙집을 등록하는 확장 단계에서 RAG 도입
- 선택: KLUE RoBERTa-large를 1차 필터로 두어 의심 문장만 Kanana로 전달
