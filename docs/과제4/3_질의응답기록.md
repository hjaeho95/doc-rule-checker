## Q1. LLM은 어떻게 문장을 이해하고 답을 만들어? (토큰, 트랜스포머)

**답변 요약**

1. **토큰**: 문장을 조각(토큰)으로 쪼개고, 각 토큰을 숫자 벡터로 변환. 요금·입력 길이 한도도 토큰 단위
2. **트랜스포머 / 어텐션**: 각 토큰이 문장 안 다른 토큰을 얼마나 참고할지 가중치를 계산. "진행했으며"를 처리할 때 앞뒤 내용을 함께 보고 두 내용이 연결됐다고 파악
3. **생성**: 다음에 올 토큰을 확률로 예측해 하나씩 이어 붙임. 수정안·JSON 모두 이렇게 생성
4. **우리 프로젝트와의 차이**: 정규식은 글자 일치만 확인 → 샘플 4의 표현 변형(4행)을 놓치고 단어만 보고 오탐(10행). LLM은 문맥으로 판단하지만 확률 기반이라 결과가 달라질 수 있음

## Q2. 3가지 모델의 작동 원리는?

**예시 입력**: 샘플 4의 4행 "…설정값을 늘린 뒤 재시험을 진행했으며 결과는 정상임"

| | ① Claude Sonnet 5.5 | ② Kanana 1.5 8B | ③ KLUE RoBERTa-large |
|---|---|---|---|
| 구조 | 디코더 (대형) | 디코더 (소형) | 인코더 |
| 읽는 방식 | 앞에서부터 다음 토큰 예측 | 같음 | 양방향으로 한 번에 |
| 우리 규칙을 아는 방법 | 프롬프트에 규칙·예시를 매번 제공 (인컨텍스트 러닝) | LoRA 미세조정으로 학습 | 규칙별 정답 데이터로 분류층 학습 |
| 출력 | 판정 + 수정안 문장 (JSON) | 판정 + 수정안 문장 (JSON) | 위반 확률만 (예: C-04 0.93) |
| 실행 위치 | 외부 API | 사내 GPU 서버 | 사내 서버 (CPU 가능) |

- ①: 규칙 검색(RAG) → 프롬프트 구성 → 어텐션으로 연결 관계 파악 → JSON 생성. 구조화 출력으로 형식 보장
- ②: ①과 같은 흐름을 사내에서 실행. 작은 모델의 부족한 실력을 우리 데이터로 보완. LoRA는 원래 모델은 고정하고 작은 보조 행렬만 학습
- ③: 형태소 분석(Kiwi)으로 연결어미 식별 → 문장을 의미 벡터로 요약 → 분류층이 위반 확률 출력. 수정안은 미리 정한 문구

**이해한 내용**

- ①은 성능이 가장 좋은 모델. 단, 직접 학습은 불가하고 프롬프트로만 맞추며 문서가 외부로 나감
- ②는 성능은 조금 떨어지지만 학습으로 최적화할 수 있는 모델. 사내 서버에서 돌릴 수 있어 보안 대안이 됨
- ③은 인코더라 판정만 가능하고, 학습을 제대로 시켜야 하며 수정안 문구도 직접 지정해야 함. 단독으로는 부족하지만 빠르고 저렴하고 결과가 항상 같아서, 의심 문장만 골라 ①·②로 넘기는 1차 필터로 쓸 수 있음

## Q3. 각 모델을 추천한 이유는?

**판단 기준 (프로젝트 조건)**: 한국어 업무 문서 / 문맥 판단 (샘플 4 놓침·오탐 해결) / 수정안 생성 / 근거 규칙 제시 / 보안 / 정답 데이터 없음 (현재)

| 모델 | 추천 이유 | 역할 |
|---|---|---|
| ① Claude Sonnet 5.5 | 문맥 판단 최상, 정답 데이터 없이 프롬프트만으로 시작, 수정안·근거 생성. 짧은 문장 단위 작업이라 Opus는 과하고 Haiku는 정확도 불확실 → 균형형 Sonnet | 주 판정 모델 |
| ② Kanana 1.5 8B Instruct | 사내 설치로 보안 해결, 한국어 특화, Apache 2.0 상업 이용 가능 (EXAONE 4.5는 비상업 라이선스로 제외), GPU 한 장으로 운영 가능한 크기 | 보안용 대안 |
| ③ KLUE RoBERTa-large | 어미 형태로 판정되는 C-03·C-04에 적합, CPU로 빠르고 저렴, 결과 일정, KLUE 벤치마크 팀 공개 모델이라 검증 자료 풍부 | 보조 필터 |

- ①과 ② 사이의 결정 기준: 회사 보안 정책이 외부 API를 허용하는가

## Q4. 인코더와 디코더의 차이는?

**답변 요약**: 둘 다 트랜스포머 구조. 차이는 글을 읽는 방향

| | 인코더 | 디코더 |
|---|---|---|
| 읽는 방향 | 양방향 (앞뒤 전부 참고) | 단방향 (앞 토큰만 참고) |
| 출력 | 문장 의미 벡터 → 분류·유사도 | 다음 토큰 예측 → 문장 생성 |
| 잘하는 일 | 판정, 분류, 검색용 유사도 | 답변, 수정안 작성, 요약 |
| 크기·비용 | 작고 빠름 | 크고 느림 |
| 비유 | 채점자 — 끝까지 읽고 점수만 매김 | 작가 — 앞 내용을 보며 다음 단어를 씀 |
| 해당 모델 | ③ KLUE RoBERTa-large | ① Claude Sonnet 5.5, ② Kanana 1.5 8B |

- ③이 수정안을 못 만드는 이유: 출력이 벡터라 문장을 생성하는 장치가 없음
- RAG의 규칙 검색 단계에서 쓰는 임베딩 모델도 인코더 → ①을 쓰는 서비스에도 인코더가 검색 담당으로 함께 들어감

**이해한 내용**: 인코더는 문장 전체를 한 번에 보고 판정만 내리는 모델이다. 디코더는 뒤 내용을 볼 수 없어서 앞 내용만 보고 다음 단어를 예측하며 글을 써 나가는 모델이다.

- 처음에는 "디코더는 뒷 내용을 추측하지 않는다"고 이해했으나, 정확히는 뒷 내용을 볼 수 없어서 다음 단어를 계속 예측(추측)하는 것이 디코더의 핵심 동작임을 확인

## Q5. RAG가 뭐고, 규칙 9개를 프롬프트에 다 넣으면 안 돼?

**답변 요약**

- **RAG (검색 증강 생성)**: LLM이 답하기 전에 관련 자료를 먼저 찾아 프롬프트에 함께 넣는 방식. 비유하면 오픈북 시험
  1. 규칙집을 조각으로 나눠 임베딩 모델(인코더)로 벡터화 → 벡터 DB에 저장
  2. 점검할 문장도 벡터화 → 의미가 가까운 규칙 검색
  3. 찾은 규칙 원문 + 문장을 LLM에 넣고 판정
- **규칙 9개는 다 넣어도 됨 (오히려 유리)**
  - 합쳐도 수백 토큰 → 컨텍스트 윈도우 대비 매우 작음
  - 검색 실수로 관련 규칙을 빠뜨릴 위험 없음
  - 매번 같은 앞부분이라 프롬프트 캐싱으로 비용 절감
- **RAG가 필요해지는 때**: 규칙이 수백 개로 늘 때 / 규칙마다 해설·사례가 길 때 / 회사별·부서별 규칙집을 따로 등록할 때 / 규칙이 자주 바뀔 때

**프로젝트 적용**

- 시범 단계: 규칙 9개 전체를 프롬프트에 넣고 캐싱 사용, RAG 미사용
- 확장 단계 (회사별 규칙집 등록): RAG 도입

## Q6. 보안이 중요하고 어차피 학습시키면 되니까 Kanana가 잘 어울리는 것 같은데?

**답변 요약**: 보안이 최우선 조건이면 Kanana가 적합. 다만 "학습시키면 된다"에는 두 가지 전제가 있음

| 전제 | 내용 | 해결 방안 |
|---|---|---|
| 정답 데이터 필요 | 규칙별로 「문장 → 판정·수정안」 예시 수백 건 필요. 현재는 샘플 4건 | 가상 문서로 학습 데이터 구축. 실제 사내 문서를 쓰지 않으므로 데이터 생성 단계에서만 상용 LLM의 도움을 받아도 보안 문제 없음 |
| 작은 모델의 한계 | C-03·C-04처럼 형태가 분명한 규칙은 학습으로 해결 가능. C-06 "이유 충분성" 같은 추론은 8B 모델이 어려울 수 있음 | AI 판정은 "권고"로만 분류되어 오판해도 검토 요청을 막지 않음 (중간평가 설계 원칙) |

**이해한 내용**: 사내 문서를 다루는 서비스라 보안을 가장 중요한 조건으로 보고 Kanana를 선택. 학습으로 최적화할 수 있지만 그러려면 정답 데이터가 필요하고, 이는 가상 문서로 만들 수 있음. 작은 모델이라 어려운 판단은 틀릴 수 있지만 AI 판정은 권고라서 업무를 막지 않음
