## Q1. LLM은 어떻게 문장을 이해하고 답을 만들어? (토큰, 트랜스포머)

**답변 요약**

1. **토큰**: 문장을 조각(토큰)으로 쪼개고, 각 토큰을 숫자 벡터로 변환. 요금·입력 길이 한도도 토큰 단위
2. **트랜스포머 / 어텐션**: 각 토큰이 문장 안 다른 토큰을 얼마나 참고할지 가중치를 계산. "진행했으며"를 처리할 때 앞뒤 내용을 함께 보고 두 내용이 연결됐다고 파악
3. **생성**: 다음에 올 토큰을 확률로 예측해 하나씩 이어 붙임. 수정안·JSON 모두 이렇게 생성
4. **우리 프로젝트와의 차이**: 정규식은 글자 일치만 확인 → 샘플 4의 표현 변형(4행)을 놓치고 단어만 보고 오탐(10행). LLM은 문맥으로 판단하지만 확률 기반이라 결과가 달라질 수 있음

## Q2. 3가지 모델의 작동 원리는?

**예시 입력**: 샘플 4의 4행 "…설정값을 늘린 뒤 재시험을 진행했으며 결과는 정상임"

| | ① Claude Sonnet 5.5 | ② Kanana 1.5 8B | ③ KLUE RoBERTa-large |
|---|---|---|---|
| 구조 | 디코더 (대형) | 디코더 (소형) | 인코더 |
| 읽는 방식 | 앞에서부터 다음 토큰 예측 | 같음 | 양방향으로 한 번에 |
| 우리 규칙을 아는 방법 | 프롬프트에 규칙·예시를 매번 제공 (인컨텍스트 러닝) | LoRA 미세조정으로 학습 | 규칙별 정답 데이터로 분류층 학습 |
| 출력 | 판정 + 수정안 문장 (JSON) | 판정 + 수정안 문장 (JSON) | 위반 확률만 (예: C-04 0.93) |
| 실행 위치 | 외부 API | 사내 GPU 서버 | 사내 서버 (CPU 가능) |

- ①: 규칙 검색(RAG) → 프롬프트 구성 → 어텐션으로 연결 관계 파악 → JSON 생성. 구조화 출력으로 형식 보장
- ②: ①과 같은 흐름을 사내에서 실행. 작은 모델의 부족한 실력을 우리 데이터로 보완. LoRA는 원래 모델은 고정하고 작은 보조 행렬만 학습
- ③: 형태소 분석(Kiwi)으로 연결어미 식별 → 문장을 의미 벡터로 요약 → 분류층이 위반 확률 출력. 수정안은 미리 정한 문구

**이해한 내용**

- ①은 성능이 가장 좋은 모델. 단, 직접 학습은 불가하고 프롬프트로만 맞추며 문서가 외부로 나감
- ②는 성능은 조금 떨어지지만 학습으로 최적화할 수 있는 모델. 사내 서버에서 돌릴 수 있어 보안 대안이 됨
- ③은 인코더라 판정만 가능하고, 학습을 제대로 시켜야 하며 수정안 문구도 직접 지정해야 함. 단독으로는 부족하지만 빠르고 저렴하고 결과가 항상 같아서, 의심 문장만 골라 ①·②로 넘기는 1차 필터로 쓸 수 있음
