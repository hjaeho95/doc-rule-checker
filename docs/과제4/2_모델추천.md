## ① Claude Sonnet 5.5 — 상용 LLM + RAG + 구조화 출력

### 작동 원리
1. 문서를 절 단위로 나눔
2. 절 내용과 관련된 규칙 원문을 규칙집에서 검색 (RAG — 임베딩 유사도 검색)
3. 「규칙 원문 + 판정 예시 + 절 내용」을 프롬프트로 LLM에 전달
4. LLM이 JSON 형식(위치·규칙 ID·위반 내용·수정안)으로 응답 — 구조화 출력(JSON 스키마 강제) 기능 사용
5. 코드가 JSON을 검증하고 "권고"로 표시

LLM은 대량의 글로 사전학습된 트랜스포머 디코더 모델. 별도 학습 없이 프롬프트 속 규칙과 예시만 보고 판정하는 것을 **인컨텍스트 러닝(few-shot)** 이라 함.

### 장점
- 문맥 이해: "~했으며"처럼 처음 보는 표현도 "내용 3개 연결"로 판단 (샘플 4행)
- "검토 결과"라는 단어가 있어도 뒤에 수치 근거가 있으면 충분하다고 판단 (샘플 10행)
- 수정안 문장 생성 가능 (개조식 변환, 문장 분리)
- 학습 데이터 없이 바로 시작. 규칙이 바뀌면 규칙집 문서만 수정
- 판정 근거(규칙 원문)를 함께 제시 가능

### 단점
- 문서가 외부 API로 전송 → 기업 계약·보안 검토 필요
- 호출량에 비례한 비용
- 같은 입력에도 응답이 조금씩 다를 수 있음 (비결정성)
- 응답 시간이 정규식보다 김 (수 초)

### 참고: 같은 계열 내 선택지 (2026-11 기준)

| 모델 | 특징 | 입력/출력 가격 (100만 토큰당) |
|---|---|---|
| Claude Haiku 5.5 | 가장 빠르고 저렴. 단순 분류 위주 | $0.10 / $0.50 |
| Claude Sonnet 5.5 | 속도와 품질 균형. 일상 업무용 | $2 / $10 |
| Claude Opus 5.5 | 최고 수준 판단력. 어려운 판정·검증용 | $4 / $20 |

- 대표 추천은 품질·비용 균형의 **Sonnet 5.5**. 정확도가 충분하면 Haiku 5.5로 비용 절감 검토

### 추천 이유
샘플 4의 두 실패(표현 변형 놓침, 단어 오탐)를 가장 확실하게 해결하고, 수정안까지 만들 수 있는 유일한 후보. 학습 데이터가 없는 현재 단계에서 바로 검증 가능.

## ② Kanana 1.5 8B Instruct — 사내 구축형 sLLM + LoRA 미세조정

### 작동 원리
1. 카카오가 공개한 Kanana 1.5 8B(80억 파라미터, 한국어 특화) 가중치를 사내 GPU 서버에 설치
2. 「문장 → 기대 판정·수정안」 예시 데이터를 수백 건 이상 준비
3. **LoRA**로 미세조정: 모델 전체가 아니라 작은 보조 행렬만 학습해 적은 GPU로 우리 규칙에 맞춤
4. 판정 흐름은 ①과 같음 (RAG + 구조화 출력)

sLLM(small LLM)은 수십억 개 파라미터 수준의 작은 LLM. 상용 대형 모델보다 성능은 낮지만 자체 서버 운영이 가능.

### 장점
- 문서가 사내망 밖으로 나가지 않음 → 보안 문제 해소
- 사용량이 늘어도 비용은 서버 고정비
- 우리 회사 문체·규칙에 특화 가능

### 단점
- GPU 서버 구축·운영 인력 필요
- 학습용 라벨 데이터(판정 정답) 수백 건 이상 직접 만들어야 함
- 대형 상용 모델보다 추론 능력이 낮아 C-06(이유 충분성) 같은 판단은 정확도 검증 필요
- 규칙 추가 시 재학습이 필요할 수 있음

### 추천 이유
보안 정책상 외부 API를 못 쓰는 경우의 현실적인 대안. ①로 품질 기준을 먼저 확인한 뒤 전환 여부를 판단하는 2단계 후보.

## ③ KLUE RoBERTa-large — 한국어 인코더 분류 모델 + 형태소 분석기

### 작동 원리
1. 형태소 분석기(예: Kiwi)로 문장을 품사 단위로 분해 → 종결어미·연결어미를 정확히 식별 (C-03, C-04 보조)
2. 한국어로 사전학습된 **인코더 모델** KLUE RoBERTa-large(24층, 3억여 파라미터)에 분류층을 붙임. 인코더는 문장을 양방향으로 읽어 의미 벡터로 바꾸는 모델
3. 규칙별로 「문장 → 위반/정상」 라벨 데이터로 미세조정
4. 판정 결과에 미리 정한 수정안 문구를 연결

### 장점
- 빠르고 저렴 (CPU로도 실행 가능)
- 같은 입력이면 항상 같은 결과 (결정적)
- 사내망 처리 가능
- 형태소 분석만으로도 "~했으며" 같은 연결어미를 품사로 잡을 수 있어 정규식보다 견고

### 단점
- 수정안 문장을 만들지 못함 (판정만)
- 규칙마다 라벨 데이터 필요
- C-06 "이유가 충분한가"처럼 추론이 필요한 판단은 어려움
- 판정 근거 설명 불가

### 추천 이유
C-03(문체)·C-04(문장 연결)처럼 **언어 형태로 판정되는 규칙**에는 가볍고 정확한 선택지. ①의 비용을 줄이는 1차 필터로 조합 가능.

## LLM의 종합 의견 (참고)

- 지금 단계(라벨 데이터 없음, 시범 운영)에서는 **① 상용 LLM + RAG**가 가장 적합
- 보안 요구가 높아지면 ②로 전환 검토
- ③은 단독보다 ①과 조합: 형태소 분석으로 C-03·C-04를 먼저 거르고, 문맥 판단이 필요한 C-06·M-01·P-02만 LLM 호출 → 비용 절감
- 최종 선정은 4단계에서 프로젝트 조건을 기준으로 결정
